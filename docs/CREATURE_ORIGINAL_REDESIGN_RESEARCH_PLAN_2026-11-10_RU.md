# Оригинальные существа Cubatarium: исследование и план переработки

Дата: 10 ноября 2026. Исследован checkout `d80a42585` (полный SHA — в приложении).
Статус: исследование выполнено; художественные решения ниже — предложения;
генератор CreatureGen, новые модели и runtime-стенд пока не реализованы.

## 1. Цель и ожидаемый результат

Переработать **все 56 существ и 5 скинов** в единую авторскую фауну Cubatarium:
новые текстуры, геометрия, силуэты, пропорции, лица и характер движения.
Особый приоритет — существам с Minecraft/Bedrock-ресурсами. Сохранить три
действующих визуальных backend и совместимость сохранений по существующим ID.

Результат — воспроизводимая библиотека исходных художественных описаний,
offline-генератор, проверенные PNG/JSON/glTF, настоящий визуальный каталог
и доказательство использования нового оформления в игре. У каждого вида
должно быть собственное решение; перекраска общей модели недостаточна.

Критерии завершения программы:

- 56/56 определений и 5/5 скинов прошли художественную и техническую приёмку.
- Во всех трёх backend есть оригинальные модели; billboard `fire_spirit`
  также включён в охват как отдельный реальный путь отрисовки.
- Для каждого выпускаемого меша, текстуры и клипа известны авторский
  источник, версия рецепта и SHA-256; нет зависимости генерации от Minecraft
  или Luanti-исходников.
- Все активные визуалы штатной поставки используют новые ресурсы: мир,
  каталог, dock, иконки, персонаж со скином и экипировкой, встроенные overlay.
- Существующие ID существ/скинов, сохранённые экземпляры, роли, habitat,
  спавн и предметные привязки сохранены либо имеют проверенную миграцию.
- Повторная сборка из одинаковых исходников даёт одинаковые пиксели и данные;
  нет новых дефектов анимации, коллизии и недопустимой стоимости отрисовки.

Это цель последующей реализации. Цель текущего исследования — подготовить
проверяемый план, а не объявить редизайн готовым после выпуска документа.

### 2.2. Minecraft-зависимость шире текстур

`tools/bedrock_geo_catalog.yaml` содержит **16 видов** с явными URL текстур
Minecraft Java 1.19.2 и файлами Bedrock-геометрии. Семнадцатый bone-вид — `bot`,
использующий humanoid-путь. Текущие `human` и `bot` ссылаются на
`geometry.zombie.v1.8`; `human` в старом каталоге импортёра описан иначе,
поэтому каталог импорта нельзя считать точным runtime-инвентарём.

У **13** существ текущий файл геометрии побайтно совпадает с локальным файлом
в `models/creatures/_sources/bedrock_geo/`: bee, bunny, chicken, cow, dolphin,
pig, sheep, skeleton, spider, squid, tortoise, wolf, zombie. Это подтверждение
совпадения файлов с локальными исходниками, а не автоматическая оценка прав
или оригинальности остальных моделей.

Для остальных четырёх bone-моделей отсутствие побайтного совпадения ничего
не доказывает: изменение UV или пары кубов уже меняет хеш. Все 17 включены
в первую производственную волну. Новая модель должна собираться из наших
описаний анатомии, а не через изменение импортированного JSON.

`models/creatures/*/LICENSE.txt` часто описывает старые Luanti-текстуры,
тогда как `diffuse.png` создавался другим импортёром. Например, у cow текст
описывает `mobs_cow.png`, а Bedrock-импортёр загружает Minecraft diffuse.
Существующий LICENSE не является достаточным manifest для всех файлов вида.
Нужно хранить происхождение **пофайлово** и отдельно для mesh/texture/animation.

Официальный `Mojang/bedrock-samples/LICENSE.md` помечает содержимое как
Mojang assets и отсылает к Minecraft EULA. Это не источник наших новых
авторских ресурсов; формат geo.json сам по себе не требует использовать
модели Mojang. [Первичный источник](https://raw.githubusercontent.com/Mojang/bedrock-samples/main/LICENSE.md).

### 2.4. Расхождения старой документации с кодом

- `docs/CREATURE_BACKENDS.md` описывает старые количества 16/36/3.
  Текущий снимок — 17/35/4.
- `fire_spirit` уже имеет `visual.sprite.billboard=true`; фабрика направляет
  его в `UCreatureVisualSprite`. Не планировать «первую реализацию billboard».
- Static glTF сейчас — `butterfly` и `octopus`. Не переносить старое
  утверждение «parts-only fire_spirit и octopus» без перепроверки.
- Реальный GPU-лимит — **96 костей**, см. `CreatureBonePaletteGpu.h`;
  максимум в текущих моделях — 67 у hermitcrab. Старые 64 неактуальны.
- Текущий `CreatureTextureStorage.cpp` загружает PNG как есть, GL_NEAREST,
  CLAMP_TO_EDGE, без генерации mipmaps. Описанный в старом документе crop
  64×64 → 64×32 в runtime отсутствует; crop есть в Bedrock-импортёре.
- `render_creature_preview_gltf.py` и `render_creature_preview_bedrock.py`
  создают файлы-маркеры `b"BMP"`. Их успешный exit не подтверждает изображение.
- В старом glTF-документе есть команда Debug; инструкция `AGENTS.md`
  требует Release и имеет приоритет для всей будущей desktop-проверки.

## 3. Что переносим из опыта растений

Исследованы `tools/assetgen.py`, `docs/ASSETGEN.md`,
`docs/WORLDGEN_PLANTS_TEXTURE_AUDIT_2026-11-02_RU.md` и текущие pack manifests.

| Уже полезный подход | Применение к существам |
|---|---|
| Детерминированные рецепты Pillow/YAML, стабильный seed через SHA-256 | Вид + часть + вариант + версия рецепта; не Python `hash()` |
| Материальные семейства и семантические роли граней | Мех/брюхо/морда/коготь/панцирь/перо; не шум на всём атласе |
| Своя структура растения: папоротник отличается от камыша | Своя анатомия: похожие размеры не превращают все виды в один quadruped |
| `qa-only`, отделение сравнения от источника генерации | Импортированные PNG и mesh только в отдельном baseline; новый build без их чтения |
| Manifest, хеши и воспроизводимая сборка | Отдельный manifest текстур, геометрии, рига, клипов, skin и итоговых ссылок |
| Контактные листы и проверки альфы | Атласы + 3D-повороты + контакт с землёй + кадры ключевых поз |
| Подключение новых leaf-текстур к worldgen | Проверка effective appearance после skin/pack overrides и копирования в bin |

Главная ошибка, которую нельзя повторить: в аудите растений от 02.11
оригинальные `cu_organic_leaf_*` уже существовали, но деревья использовали
старые `mt_*` ресурсы. Позже это было исправлено подключением и проверкой
потребителя. Для существа «PNG создан» означает только промежуточный артефакт.
Готовность означает, что **правильный файл реально разрешён и нарисован**.

Не переносить block-specific логику буквально. Существо имеет UV-швы,
суставы, меняющуюся позу, лицевую сторону и skin overrides. Бесшовная
квадратная текстура блока не решает задачу анатомического атласа.
Не расширять монолитный `assetgen.py` вторым монолитом: переиспользовать
малые проверенные функции seed/палитры/manifest, вынеся общие только там,
где это не меняет существующие результаты растений.

## 4. Внешнее исследование: применимость и решения

Проверены первичные источники 10.11.2026. Ниже явно отделены свойства
инструментов от предложенных архитектурных решений Cubatarium.

| Источник | Что подтверждает | Решение для проекта |
|---|---|---|
| [Blockbench: Entity Modeling](https://blockbench.net/wiki/guides/bedrock-modeling/) | Работу с костями, pivots, UV, текстурой и анимацией | Использовать для ручной доводки наших исходников; сначала shape, потом atlas |
| [Blockbench: 3D Export](https://blockbench.net/wiki/guides/export-formats/) | glTF экспортирует иерархию и анимацию; экспорт хуже исходника для дальнейшего редактирования | Хранить авторские исходники отдельно от runtime glTF; предусмотреть импорт проверенных правок |
| [Blockbench: Animation Expressions](https://blockbench.net/wiki/guides/animation-expressions/) | При glTF-экспорте выражения запекаются в ключи; динамические переменные так не переносятся | Запекать авторские циклы offline; скорость/состояние связывать в Cubatarium |
| [Khronos glTF 2.0](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) | Контракт mesh/UV/skin/weights/inverse bind и animation channels | Валидировать экспортер по спецификации и по более узкому runtime-контракту |
| [Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator) | Проверяет JSON, ссылки, бинарные accessor-данные и animation inputs/outputs | Подключить как второй независимый валидатор, закрепив версию; не заменяет просмотр |
| [Greg Turk: Reaction-Diffusion](https://sites.cc.gatech.edu/gvu/people/faculty/greg.turk/reaction_diffusion/reaction_diffusion.html) | Синтез пятен и полос на поверхностях | Опциональный offline-эксперимент для крупных рисунков, после простых управляемых масок |

### 4.1. Сравнение подходов

| Подход | Сильная сторона | Ограничение | Выбор |
|---|---|---|---|
| Перекрасить старые атласы | Быстрое временное отличие | Старый силуэт, UV и узнаваемые мотивы остаются | Не считать финальной переработкой |
| Все модели вручную | Точный художественный контроль | Дорого повторять 56 раз, риск потери воспроизводимости | Ручной concept и контрольные образцы обязательны |
| Один параметрический шаблон на всех | Быстрое массовое покрытие | Теряется анатомия и индивидуальность | Общие primitives, несколько семейств, отдельный рецепт каждого вида |
| Семантические модели + процедурные материалы + ручная доводка | Масштабирование и управляемый стиль | Нужны exporters и визуальная QA | Рекомендуемая основа |
| AI-image как финальный атлас | Быстрые варианты цвета/настроения | Нестабильная анатомия и UV, швы и сложная регенерация | Только необязательный concept, с отдельной provenance |
| AI-3D → автоматический runtime | Быстрые крупные формы | Риг, веса, число полигонов, стиль и экспорт требуют обработки | Не зависимость критического пути |

Вывод исследования: масштабировать следует **процесс авторского дизайна**,
а не случайные текстурные вариации. Генератор — инструмент сборки и
воспроизведения художественных решений. Он не заменяет выбор силуэта.

## 5. Предлагаемое художественное направление

Рабочая концепция — **«Живой атлас Cubatarium»**: геометрическая фауна,
согласованная с нашей флорой и материалами мира. Это предложение для первых
образцов, не утверждённый пользователем окончательный стиль.

Существа сохраняют читаемую биологию, но получают собственные отношения
масс, форму морды, расположение глаз, пластику хвоста/конечностей и рисунок.
Животные могут оставаться коровой, лисой или китом: уникальность не требует
сделать каждого фантастическим гибридом. Монстры получают более свободную
анатомию. Не превращать всё в камень, не добавлять всем кристаллы и рога.

Шесть согласованных направлений:

1. **Луговые и домашние:** мягкие ступенчатые объёмы, тёплая шерсть,
   спокойные крупные отметины. Читаемость рядом с травами и цветами.
2. **Лесные:** вытянутые/низкие силуэты по экологии, охра, кора, хвоя;
   маски и полосы направлены по телу, без буквального копирования листвы.
3. **Птицы и насекомые:** узнаваемый размах, характерная посадка,
   крупные перьевые или хитиновые секции; небольшие цветовые акценты.
4. **Водные:** ясная ось тела, контраст спины и брюха, непрерывные
   продольные рисунки; плавники и щупальца читаются в движении.
5. **Амфибии и холод:** отдельные позы на суше/в воде, спокойные
   бело-серые/синие массы с небольшими контрастными ориентирами.
6. **Фантастические и враждебные:** структурная связь с грунтом,
   корнями, минералами или жаром; у каждого своя масса и манера движения.

Правила art bible:

- Сначала чёрный силуэт в 3/4 и сбоку, затем 3–5 крупных цветовых зон,
  затем лицо и только после этого микродетали.
- На один материал исходно 4–6 тонов; число цветов и плотность деталей
  откалибровать на пилотах, а не превращать это в универсальный жёсткий лимит.
- Базовый масштаб деталей ориентировать на 16 texels/block мира.
  Размер **атласа** зависит от площади частей, это не обязательно 16×16.
- Проверять отличимость вида в ч/б, при маленьком экранном размере и ночью.
  Тонкие полосы, существующие только в PNG крупным планом, не считать признаком.
- Мех направлять вдоль анатомии, перья группировать, панцирь строить плитами,
  брюхо отделять управляемой маской; не заполнять всё случайным шумом.
- Один главный и два вторичных характерных признака на вид. Минимум одно
  собственное idle-действие или характерная фаза locomotion.
- Для новой фантастической формы проверять читаемость угрозы и способа
  движения; новый силуэт не должен скрывать момент атаки.
- Художественные названия в таблицах — рабочие. Runtime-ID сохраняются.

Для каждого пилота подготовить три различающихся concept-направления,
выбрать одно по силуэту, качеству в мире и стоимости производства. Не
генерировать десятки случайных цветовых seed вместо вариантов формы.

## 7. Архитектура CreatureGen

### 7.1. Источники и поток данных

Предлагаемые новые файлы, **пока не существуют**:

```text
tools/creaturegen.py                  CLI, короткий dispatcher
tools/creaturegen/                    schema, anatomy, materials, uv, exporters, audit
tools/creature_catalog_original.yaml  все 56 стабильных ID, концепт, seed, backend
tools/creature_recipes/               анатомия и художественные параметры по видам
tools/creature_palettes.yaml          общие материалы и семейные палитры
assets_src/creatures/<id>/            контролируемые авторские модели и правки
assetgen_output/creatures/staging/    кандидаты; не видны runtime автоматически
models/creatures/<id>/               проверенные runtime PNG/JSON/glTF
models/skins/<id>/                   проверенные skin JSON/PNG
models/creatures/asset_manifest.json  пофайловое происхождение и версии
```

Поток: concept → семантическое описание анатомии → модель/риг → UV и маски
частей → текстурные рецепты → один из трёх exporters → staging → validate →
настоящий render → игровая QA → адресная публикация ресурсов → обновление manifest.

Импортированный baseline хранится отдельно; production build проходит и при
недоступной `E:/Work/Home/CubatariumTextureResearch` и `_sources/bedrock_geo`.
Старые импортёры не вызываются новой сборкой. При необходимости оставить их
как явно исследовательские инструменты; не удалять исходники/атрибуции
до завершения миграции и проверки ссылок пакета поставки.

Общий слой описывает семантику: `body`, `head`, `muzzle`, `belly`, `leg_fl`,
`tail`, `wing_l`, `shell`, anchors, симметрию, направления рисунка и измерения.
Это **не общий runtime-скелет**. У backend остаются разные иерархии, матрицы,
правила UV и анимации. Не объединять `BoneSkeletonHierarchy` с glTF skinning.

Геометрия, текстуры и клипы могут иметь ручной авторский источник вместо
процедурного рецепта. Он тоже версионируется и включается в manifest;
последующая генерация не должна стирать ручную доводку. Для каждого вида
указать один канонический источник и направление экспорта.

### 7.2. Контракт описания вида

Минимально: ID, backend, family, authoring_source, seed, recipe_version,
palette_id, anatomy parameters, semantic parts, rig mapping, UV layout,
texture roles, required clips/profiles, anchor points, intended bounds,
skin variants, provenance, QA state, ссылки на контрольные изображения.

Bounds — геймплейный контракт. Отдельно хранить visual envelope в движении
и collision envelope; не раздувать коллизию по декоративному усу или крылу.
Статические габариты проверять автоматически, extrema клипов — выборкой;
где требуется большой рост формы, сначала согласовать новую коллизию и
прогнать спавн/навигацию, затем считать вид завершённым.

Публикация атомарная на уровне вида: модель, bin, текстуры, JSON, skins и
manifest одной ревизии. Если одна проверка не прошла — остаётся предыдущая
версия. Не выпускать JSON со ссылкой на ещё не опубликованный файл.

### 7.3. Три backend-адаптера

| Backend | Что генерировать | Известный контракт и риск |
|---|---|---|
| B | Свой geo.json, один diffuse atlas, profile/rig mapping | Box UV использует размеры куба в model units; текущие poses знают имена костей |
| G | Свой mesh, skin/weights/inverse binds, UV, external buffers, именованные клипы | Runtime реализует подмножество glTF; валидный внешний export ещё не означает поддержку |
| R | parts в `rigid_model.json` либо штатном `visual.parts`, pivot/limb, role-textures | Не потерять внешнюю модель и назначения presenter; не рисовать лицо на всех сторонах |
| Sprite внутри R | Своя `body` RGBA текстура и штатные billboard/emissive параметры | Не создавать четвёртый backend и не отключать существующую фабричную ветку |

**B:** сначала сохранить технические имена костей, которые уже использует
`BoneSkeletonPoseEngine.cpp` (`leg0…`, `body`, humanoid `rightArm` и т. д.).
Это технический интерфейс, не художественный образ. Для более сложной
анатомии добавить явное semantic bone mapping и тест; не переименовывать
косточки без изменения потребителя. Свой humanoid должен сохранить anchors
`rightItem`/`leftItem` и контракт экипировки. Для новых пропорций проверить
eye height и crouch; сам факт новой геометрии не обновляет их автоматически.

**G:** текущий `CreatureGltfLoader.cpp::MaterialTextureStem` использует
`materials[].name` как texture stem. Экспортёр должен явно приводить материалы
к согласованным именам `body/face/...` и проверять каждую ссылку.
Нельзя полагаться только на `images[].uri` или embedded texture обычного
Blockbench-export. Текущий loader читает внешние buffers; GLB/data URI
не считать поддержанными без отдельной реализации и проверки.
Первые exports — внешние `.gltf` + `.bin`, только уже поддержанные каналы
и атрибуты. Не добавлять PBR/normal map/morph target в критический путь.

**R:** заменить все три demo собственными сборками, сохранив purpose
walker/flyer/swimmer и habitat. Рендер этого backend должен оставаться
полноценным. Не решать задачу переводом всех видов на glTF.

### 7.4. Текстуры по анатомии

Генерация проходит слоями: базовый материал → маски спины/брюха/морды →
крупный рисунок → directional detail → глаза/клюв/когти → seam padding → audit.

Для первых пилотов достаточно масок и крупных пятен/полос на поверхности.
Reaction-diffusion экспериментировать offline на одном виде, сравнивая
управляемость и время итерации. Не вводить сложный симулятор до получения
лучшего результата, чем у простых авторских масок.

Координаты рисунка задавать в пространстве тела/части, затем запекать в UV.
Не считать соседние острова атласа соседями на поверхности. На границах
частей проверять совпадение крупных полос и порядок слоёв. Для меха нужны
плотные поверхности; для крыльев/плавников — управляемые прозрачные области.
Нельзя применять общий opaque-fill ко всем материалам.

Текущие creature shaders принимают albedo/alpha, tint, свет и fog;
универсального glTF PBR-материала здесь нет. Skinned fragment shader
отбрасывает alpha < 0.05 и выводит opaque alpha для оставшихся пикселей.
Поэтому стеклянные крылья/полупрозрачные слизни и per-material emissive
не обещать без отдельного shader-pass этапа. Светлые прожилки можно
выполнить цветом; реальное свечение — отдельное проверяемое свойство.

### 7.5. Воспроизводимость и происхождение

Manifest на каждый файл: вид, роль, авторский input и его hash,
генератор/версия, pinned зависимости, seed, размеры, pixel hash для PNG,
file hash, назначение runtime и статус QA. Для мешей и клипов — отдельные
записи, даже если они лежат в одном glTF.

Сравнивать и file hash, и нормализованный pixel/data hash: метаданные PNG
не должны маскировать фактическое равенство пикселей. Проверка дубликатов
ловит случайно одинаковые результаты, но не доказывает оригинальность.
Для художественной оценки нужны силуэты, рисунки и человеческий просмотр.

Базовая production-политика — только наши авторские inputs. Старые
исходники используются для baseline-сравнения в отдельном процессе,
не для patch synthesis, tracing, перекраски, копирования UV или mesh.
Не переносить метку CC0 с растений автоматически на новые файлы: итоговая
лицензия и авторство должны соответствовать действительным источникам.

## 8. Визуальный стенд и критерии приёмки

### 8.1. Сначала сделать настоящий стенд

Текущие BMP-маркеры оставить явно помеченными wiring smoke либо заменить
на реальные кадры. Новый стенд должен использовать те же loaders, pose и
draw пути, что мир/GUI. Отдельный красивый Blender-render допустим для
дизайна, но не подтверждает совместимость игры.

Для каждого вида сохранять:

- Идентичность: source revision, backend, resolved model/texture keys,
  active skin/overlays, размеры/число костей/примитивов и cache revision.
- Не менее 8 yaw-ракурсов, сверху и снизу; чёрный силуэт и обычный цвет.
- Настоящие PNG в rest и характерных фазах движения, дополнительно короткий
  motion capture; фаза и время фиксированы для сравнения.
- Полный кадр мира и крупный кадр, dock preview, иконка, при наличии скин.
- Для humanoid — броня и предметы в обеих руках; для amphibious — суша и вода;
  для billboard — светлый/тёмный фон и поворот камеры.

Для 56 видов 8 ракурсов × 3 базовые позы — минимум 1344 изображения до
добавления UI и сцен. Организовать листами по виду/семейству, не выдавать
тысячи несвязанных картинок. PNG нужно открывать и проверять как изображения;
нулевой exit и наличие файла недостаточны.

|---|---|---|
| Полнота | 56/56 + 5/5, каждый ID встречается ровно один раз | Сверка live catalog ↔ original catalog ↔ manifest ↔ QA |
| Оригинальное производство | Новый build не читает reference assets; нет их в штатном dependency graph | Изолированный build + пофайловая provenance + inspection release package |
| Художественный вид | Различимы силуэт/лицо/крупный рисунок/движение; нет узнаваемой композиции исходного моба | Листы baseline/new, просмотр без текстур и в цвете; явный reviewer verdict |
| UV | Нет missing stems, растяжения лица на корпус, швов крупных мотивов, неправильного mirror | UV-checker и реальные ракурсы |
| Rig | Нормальные веса и inverse bind; части не расходятся; все обязательные состояния разрешаются | Проектные tests + Khronos validator + sampled motion capture |
| Габариты | Стопы/дно совпадают с опорой, коллизия соответствует принятому envelope, mesh не исчезает на границе кадра | Bounds audit + игровые кадры/пробы culling |
| Appearance | Новые файлы реально выбраны после skins/overlays, нет старой иконки | Лог resolved keys/hashes + мир/dock/icon + чистый повторный старт |
| Совместимость | Старые экземпляры и skins грузятся, экипировка остаётся на anchors | Копия старого save + новый save + reload |
| Производительность | Кости ≤96; стоимость не выходит за откалиброванные пилотами бюджеты | Тот же Release EXE/scene/количество видимых, CPU/GPU/frame/memory |
| Полнота доказательств | Все обязательные артефакты есть и читаются | Missing/invalid = FAIL либо UNTESTED, никогда PASS |

Художественный гейт не заменять одним SSIM/pHash: изменение нескольких
пикселей или масштаба сломает простую метрику, сохранив узнаваемый дизайн.
«Достаточно оригинально» нельзя автоматически вывести из отличающегося SHA.

Предварительные бюджеты для пилотов: один atlas/material у простых видов,
обычно до 2–3 у сложных; 64×64/128×64, при обосновании 128×128; избегать
роста на порядок относительно baseline. Для G удерживать типовой rig
компактным, 96 — технический потолок, не целевое число костей. Число
треугольников, draw calls и память сначала измерить по видам; затем зафиксировать
лимиты по семействам. Предложенный относительный performance-гейт — не более
10% роста p95 creature-pass CPU/GPU в сопоставимой сцене после учёта шума;
это плановый порог, текущие замеры его не подтверждают.

## 10. Проверки и рабочая дисциплина

Планируемые CLI-команды CreatureGen: `inventory`, `build --species`,
`build --all --staging`, `validate`, `compare`, `publish --species`,
`audit --effective`. Их имена здесь — проект интерфейса, они пока не работают.

Реально существующие проверки для использования по ходу изменений:

```powershell
python tools/validate_gltf_creature.py --all
python tools/test_gltf_skinned_bind_pose.py
python tools/validate_bedrock_creature.py
```

Третья команда сейчас FAIL и неполна по coverage — это baseline, который
нужно исправить. Она не должна оставаться обязательной «зелёной» проверкой,
искусственно пропускающей три вида или bot. `creature_bounds_audit.py --check`
полезен для существующих glTF-граней, но не заменяет envelopes анимации,
bone/rigid/sprite-проверки. Его собственные output side effects нужно учесть.

При изменении runtime применять релевантные C++ tests из CMake:
`creature_visual_backend_select_test`, `creature_appearance_test`,
`creature_model_integrity_test`, `creature_bone_skeleton_loader_test`,
`creature_gltf_loader_test`, `creature_gltf_clip_test`,
`creature_skinned_draw_test`, `creature_shader_parity_test`.
Тестовые таргеты собирать только в Release и запускать `ctest -C Release`
с выбором нужных тестов; наличие имени в CMake не означает готовый exe.
Приложение собирать строго командой из §8.3.

Новые содержательные проверки: реальная связь catalog↔manifest↔output;
повторная генерация в двух чистых каталогах; UV bounds и required stems;
valid image decoding; невозможность PASS без кадров; позы и привязки anchors;
изолированная сборка без references; resolved runtime appearance. Не создавать
snapshot-тест, который просто закрепит случайно плохой шум или текущий импорт.

Состояние каждого вида вести раздельно:
`planned → concept_selected → authored → exported → structural_pass →
visual_pass → runtime_pass → accepted`.
Промежуточные `texture_only`, `blocked`, `needs_art_revision` не равны accepted.
Завершённость программы — число `accepted`, а не количество PNG/коммитов.

## 11. Риски, варианты и нерешённые вопросы

| Риск | Как обнаружить рано | Ответ |
|---|---|---|
| Получатся перекрашенные Minecraft/Luanti-мобы | Силуэт без текстуры рядом с baseline | Авторская геометрия с нуля, не правки копии |
| Все виды станут одним шаблоном | Семейные листы, сравнение пар близких видов | Отдельный anatomy recipe и 3 характерных признака на вид |
| Новый атлас не используется | Resolved keys + cache revision + фактический кадр | Сквозная QA с пилотов, исправление overlays и bin sync |
| Художественный export превышает runtime-возможности | Ранняя загрузка B/G/R образцов | Явный поддерживаемый subset и exporters; shader features отдельно |
| Изменённые пропорции ломают игру | Anchors/eyes/bounds, старый save, navigation | Сначала удерживать collision envelope, расширения отдельно проверять |
| Риг «рассыпается» только в движении | Выборка всех обязательных клипов | Новые weights/bind/rig, не маскировать изменением bounds |
| Невозможно воспроизвести ручной результат | Clean rebuild и сравнение hashes | Канонические editable sources и явные artist overrides |
| Большой объём при слабом результате пилотов | Gate C4, реальное время на вид | Пересчитать план до массовой волны |
| Старая атрибуция скрывает смешанные ресурсы | Пофайловый manifest и package graph | Учитывать mesh/PNG/clip отдельно; удалять только подтверждённо заменённое |

До масштабирования должны быть разрешены: выбранное художественное
направление по реальным пилотам; точный режим artist overrides; budgets
по backend/семейству; реализация runtime capture; совместимость humanoid
скинов и anchors; фактическое поведение отсутствующих diffuse в baseline.
Эти вопросы можно проверять в C0–C4; они не мешают принять общий план сейчас.

Вне обязательного объёма: полная переделка AI/спавна, размножение, пищевые
цепи, новый combat, четвёртый backend и массовый перевод на один renderer.
Характерные визуальные движения входят в объём. Новые сложные поведения
сначала демонстрировать через имеющиеся состояния; необходимые расширения
оформлять отдельным небольшим заданием, чтобы не сорвать художественную цель.
