# PERF-0.4: профилирование populate целиком

Дата: 2026-11-04. Ветка: `feature/perf-0-4-populate-profiling`.
База: `develop` после PERF-0.3 (`c3eb9d889`).
План: `docs/WORLDGEN_TAILS_REWORK_PLAN_2026-11-03_RU.md`.

## 1. Реализованная телеметрия

1. `ChunkPopulateDiagnostics` теперь накапливает все завершённые populate-задания,
   а не только последний чанк. Отменённые задания учитываются отдельно и не попадают
   в распределения завершённых чанков.
2. Для total/sample/terrain/carve/post/seal сохраняются count, сумма, median, p95 и max.
3. В `post` при активном `CUBATARIUM_WORLDGEN_SEAL_AUDIT` измеряется каждая включённая
   стадия из фактического порядка pipeline: geology, ores, vegetation, ground cover,
   decoration, structures и остальные. Таймеры суммируются по 256 колонкам чанка.
4. Внутри чанка отдельно измеряются mudflow, pocket seal, permeable seal, повторный
   pocket seal и prune. Добавлены счётчики посещённых колонок, перемещённых mudflow
   вокселов, заполненных жидкостью вокселов, изменённых permeable-колонок и удалённых
   prune вокселов.
5. Сводка `chunk_populate_summary.v1` сохраняется в `movement_diagnostics.json`.
   Flight-sim теперь записывает этот файл рядом с `flight_sim_report.json` до быстрого
   завершения процесса, которое не выполняет обычное сохранение мира.

Алгоритмы генерации и их порядок не изменены. Подробные таймеры по-прежнему включаются
только флагом аудита, поэтому эти прогоны нельзя считать чистым FPS baseline.

## 2. Протокол

Release `Cubatarium`, 1280×720, `--metrics`, одна исходная копия
`World_242_perf_baseline_source`. Для каждого маршрута создана новая рабочая копия;
пользовательский `World_242` не изменялся.

- 8 с начального idle;
- 70 с sprint-полёта на запад без телепортации, level-forward;
- 30 с остановки;
- анализ с warmup 20 с;
- `CUBATARIUM_WORLDGEN_SEAL_AUDIT=1`.

Итоговые прогоны: `moving_2` и `moving_3`. Промежуточный `moving_1` был выполнен до
добавления экспорта сводки рядом с report и в численные таблицы не входит. Оба итоговых
приложения завершились штатно (`exit_code=0`). Универсальный `pass=false` вызван
существующими performance/readiness gates; этап добавляет диагностику и не объявляет
эти gates исправленными.

Decoration — крупнейший и наиболее хвостовой класс post. Сильная разница median между
прогонами при повторно высоких p95/max указывает на неоднородность по типам чанков/правил,
а не на равномерную стоимость каждой колонки. Следующий инструмент должен раскладывать
Decoration по правилам/pools и считать кандидатов, посещённые object voxels и отклонённые
размещения. Нынешних данных недостаточно, чтобы выбрать конкретное ускорение без риска
изменить содержимое мира.

Ores — второй устойчивый вклад. Structures дешевле на два порядка и не является
приоритетом по этому маршруту.

## 5. Профиль seal

| Стадия | moving_2 median, мс | moving_2 p95, мс | moving_3 median, мс | moving_3 p95, мс |
|---|---:|---:|---:|---:|
| pocket seal | 56,97 | 127,73 | 78,80 | 142,95 |
| permeable seal | 121,18 | 230,47 | 138,62 | 224,99 |
| pocket reseal | 0,00 | 114,18 | 0,00 | 83,00 |
| vegetation prune | 24,69 | 39,14 | 28,20 | 74,57 |

Permeable seal даёт 52,49% и 51,98% суммарного seal в двух прогонах. При этом в каждом
прогоне обойдены 256 колонок на чанк, но изменённых permeable-колонок всего 2658 на
прогон; это подтверждает значительную долю проверок без изменения. Pocket reseal
выполняется не для каждого чанка: нулевая медиана ожидаема, ненулевой p95 показывает
условно дорогой хвост.

Mudflow на активной конфигурации отключён: его счётчики и таймеры равны нулю. Это не
доказательство бесплатности mudflow на других профилях.

## 6. Связь с кадровыми всплесками и отставанием мира

В `moving_2` 123 из 124 spike-записей имеют положительный generation backlog; в
`moving_3` — 4 из 5. Это подтверждает совпадение тяжёлых кадров с давлением фоновой
генерации на маршруте, но **не измеряет непосредственную стоимость populate в main thread**.
Worker-таймеры выполняются асинхронно. Для причинной атрибуции дополнительно нужны commit
apply/seal, захваты snapshots, блокировки и admission/relight/mesh этапы на main thread.

Наибольший spike около 737–756 мс в обоих прогонах имеет нулевой generation backlog и не
может быть объяснён текущим populate только по этим данным. Остальные moving-gates всё ещё
показывают высокие dirty/not-ready и незавершённое восстановление после остановки. Таким
образом, этап локализует задержку появления нового содержимого, но не утверждает, что
исправлены отставание визуала, дыры при удалении блоков или готовность света.

## 8. Решение по следующей оптимизации

PERF-0.4 принят: известны доли стадий populate и устойчиво выделены Decoration, Ores,
permeable/pocket seal и prune. GEN-1.2 (единый coarse path) остаётся обоснованной работой,
но её ожидаемый потолок ограничен примерно 10–11% текущего суммарного populate, а не
обещанными ранее 2–3× для полного чанка.

Следующий измерительный шаг перед оптимизацией содержимого: декомпозировать Decoration по
правилам/pools и числу object-voxel проверок, затем отдельно профилировать внутренние
проходы permeable seal. Оптимизации выбирать после parity snapshot, с нулевым content drift.
