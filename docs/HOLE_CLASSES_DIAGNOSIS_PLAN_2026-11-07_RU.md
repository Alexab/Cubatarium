# План диагностики и исправления: классы видимых дыр (пустота и чёрные блоки)

Дата: 2026-11-07. База: `develop` после серии PERF-0.29…0.33.

## 1. Наблюдение пользователя

- Дыры видны **внутри кольца**, минимум два вида: **пустота** (виден задний план — вода/небо) и **чёрные блоки**.
- Ключевая улика: **дыра мгновенно закрывается при установке блока в неё**. Установка блока → edit → dirty → rebuild с *текущими* данными соседей → меш корректен. Значит:
  - меш в дырявом чанке **существует** (census считает колонку Ready);
  - он построен по **неверным входным данным** (устаревший сосед / незасеттлившийся свет);
  - повторная сборка по правильным данным дефект устраняет.
- Телеметрия эталонных прогонов показывала `visual_holes=0` — детектор считает *отсутствующие* меши, а не *неверные*. Класс дефекта был невидим для метрик.

## 2. Почему приёмочные прогоны это не поймали

1. Все acceptance-прогоны серии шли с `CUBA_VISUAL_BLACK_TRACE_CPU_ONLY=1` — **пиксельные пробы были отключены** (анти-шумовая мера из PERF-0.11). Классификация пикселей (stale/black/void, `renderer_pixel_rgba`) в них не выполнялась.
2. `near_focus_hole_probe` проверяет отсутствие *меша* (resident/Drawable), а не корректность граней.
3. Census-класс Ready выставляется по `HasMeshSatisfyingColumnReady` — меш с дырками в гранях проходит как drawable.

## 3. Классы дефекта и гипотезы (с якорями)

### A. Пустота (просвет к воде/небу) — неверная геометрия published-меша

- **A1 (главная гипотеза): прием устаревшей геометрии.** Конвейер публикует меши, собранные против устаревших входов: `MeshApplyStaleInputReason::Geom` при `accept_input_stale` → `MeshApplyStaleGeomAcceptedCount` (`src/Render/Mesh/ChunkMeshCache.cpp:6672-6676`). В эталонных прогонах `mesh_apply_stale_geom=102`, `mesh_apply_stale_geom_accepted=146` — сотни принятых «stale-geom» мешей за полёт. Меш, построенный против неверных данных соседа, публикуется → дырка в гранях → «закрывается при установке блока» (rebuild по актуальным данным).
- **A2: пропуск инвалидации при загрузке/изменении соседа.** Если чанк замешен при незагруженном/пустом соседе, грани в его сторону срезаны; приход соседа должен инвалидавать dependent (ReadSet-стампы отсутствия: `CollectColumnChunkCoords` записывает отсутствие — `ChunkRelightSnapshot.cpp:39`; для меша — dependency invalidation `QueueMeshDependencyInvalidation`). Проверить, покрывает ли стамп absent-соседа сценарий «сосед загрузился позже» и не теряется ли инвалидация на путях partial-reload/soft-defer.
- **A3 (регрессионный риск серии PERF-0.30): `RebaseDesiredToPublished` маскирует реальные долги.** Rebase вызывается из reclaim при `fruitless>=2` (`World.cpp:3063`): если незавершавшаяся сборка была *реально нужна* (устаревший меш), rebase стирает demand → устаревший меш остаётся → дыра. Независимые stale-сканы ловят только световую устарелость, не геометрическую против соседей.
- **A4: deferred-ring/диет удерживал координату, demand запаркован (`IsOutsideScheduleFocus`/`IsRemeshDeferred`) — остановка легитимно не строит rim, но дыры пользователь видит и внутри фокус-радиуса → этот класс не объясняет наблюдение; проверить в witness и отсеять.**

### B. Чёрные блоки — FullyDark грани при незасеттлившемся/потерянном свете

- **B1: relight-долг потерян при видимых тёмных гранях.** На скриншоте `Relight: p=0 bg=0 inflight=0` и `RelightQueue: p=0 bg=0` — релайт-очереди пусты, тёмные грани при этом видны. Кто должен поднять demand: `OnLitPendingNeeded` → pending-light маркер → relight; либо stale-light debt (`PendingStaleLightRemeshes_`). Проверить обе цепочки на этих чанках: маркер отсутствует? debt очищен ошибочно (`event=published` при `own_light_current && halo Matches` — ложный pass)?
- **B2: accept stale-light мешей** (`MeshApplyStaleLightAcceptedCount`, сотни за полёт): меш собран до засеттливания света и принят → чёрные грани до следующего rebuild; если последующий rebuild не назначен (см. A3) — чёрнота постоянна.
- **B3: листва/прозрачность.** Дыры на скриншоте окружены листвой; свет через листву (permeable/leaf alpha) мог оставить грани тёмными при легальном наборе света — отделить «дефект» от «легальной темноты» по скину блока.

## 4. Диагностические этапы (каждый — witness до изменений)

### H-1. Пиксельный witness с пробами (без CPU_ONLY)

- Полёт по маршруту с лесом/водой внутри кольца (мир со скриншота; если это не World_223 — снять имя мира из сейва), `CUBA_VISUAL_BLACK_TRACE=1` **без** `CPU_ONLY`, с `PIXEL_PROBE_STRIDE` и focus-probes.
- Зафиксировать: пиксельные пробы классов stale/black/void в моментах, соответствующих дырам; `renderer_pixel_rgba` и координаты чанков проб.
- Критерий этапа: воспроизводимый набор координат дыр обоих классов + их пиксельная классификация.

### H-2. Корреляция координат дыр с механизмами

Для каждой дырявой координаты из H-1 снять (focus_slice_trace/demand_transition_trace + погружение в лог):
- `mesh_apply_stale_geom_accepted` факт: публиковался ли меш этого чанка как stale-geom (A1);
- таймлайн соседей: строился ли меш до загрузки соседа; стреляла ли инвалидация при приходе соседа (A2);
- попадал ли чанк в `RebaseDesiredToPublished` (счётчик rebase — добавить в watchdog при отсутствии) (A3);
- световое состояние: `has_settled_light`, `field_light_rev` vs `meshed_light_rev`, halo state, наличие чанка в `PendingStaleLightRemeshes_` (B1/B2).

### H-3. Ревизия регрессий серии PERF-0.30

- A3: точечный аудит rebase — добавить счётчик и (по результату H-2) либо гейтить rebase проверкой «published mesh content revision == текущий content revision чанка» (ребейз только когда published-меш действительно актуален по контенту), либо убрать rebase для записей с геометрией позади при живом контенте.
- Проверить, что парковки (`IsOutsideScheduleFocus` и др.) не гасят demand чанков внутри фокус-радиуса.

### H-4. Сборка и фикс (по результатам H-1…H-3, по одному дефекту за шаг)

Ожидаемые направления (порядок по вероятности из H-2):
1. Запретить публикацию stale-geom мешей (или обязать requeue с актуальным capture) — A1.
2. Гейт rebase / восстановление честного demand — A3.
3. Инвалидация dependent при приходе соседа — A2 (если подтвердится пропуск).
4. Восстановление relight-долга при FullyDark без очереди — B1.

## 5. Критерии приёмки

- Пиксельный witness H-1 после фикса: ноль void/black проб в устойчивых состояниях внутри кольца (транзитные при движении — по базе PERF-0.31).
- Эталонный cruise/stop: `face_debt=0`, `miss_end=0`, stop dirty=0, missing/ready не хуже базы, FPS без регрессии (база серии: wall fly ~20 мс, ~50 FPS).
- Ручная проверка пользователя на скриншотном месте: дыры обоих классов не воспроизводятся; установка блока больше не является «лечением».
- Контрольные юнит-тесты зелёные; новые кейсы — на найденный класс (например, «stale-geom не публикуется»).

## 6. Правила (неизменно)

- Один дефект — одна ветка, witness до изменения, Release-сборка, merge `--no-ff`.
- Не маскировать счётчики; rebase/паркинг — только для доказанно фиктивных желаний.
- Пиксельные пробы — только в диагностических прогонах (opt-in).

## 7. Результаты H-1/H-2 (2026-11-07, `bin/suite_reports/holes_h1/world245`)

Мир: **World_245** (последний созданный, совпадает со скриншотом). Witness: resume из сохранённой позиции, полёт 30 с + остановка 45 с, пиксельные пробы (stride 30), 9120 проб.

### Класс B (чёрные блоки) — локализован точно

- **56 чёрных проб** (lum<35 при draw_ready=1), кадры 30–450 — **load-фаза мира**, чанки spawn-кольца (JSONL-пространство (-5..0, 3, 0..20)).
- Световое состояние чёрных чанков: `meshed_light_rev = field_light_rev = 1`, `settled=1`, `vertex_sky_light=1` (почти ноль неба) — **световое поле застыло на начальной ревизии 1**, «settled»-proof принят для no-change результата.
- Проверки, которые пропустили дефект: stale-скан сравнивает meshed vs field (равны → не stale); halo сравнивает с соседями (у соседей тоже rev 1 → «Matches»). Регион rev-1 чанков самосогласован → вечная чернота до ручного edit (edit запускает честный relight → «дыра закрывается при установке блока»).
- Open-sky машина touched 1 чанк из выборки; после кадра 500 чёрных проб нет — класс концентрируется в load-фазе первого запуска мира (скриншот пользователя — первый запуск World_245).

**Гипотеза B-механизма:** load-time relight оставил часть чанков на начальном поле; settle-proof принял «no-change settlement» (включая revision 1) как завершение; корректирующий relight больше не назначался (очереди пусты: `Relight p=0 bg=0`).

**Направление фикса B:** sanity-гейт settle-proof — для колонки, открытой небу (нет solid над верхом), settled свет с vertex_sky≈0 на верхней грани не принимается; вместо этого поднимается реальный relight (pending-light/relight demand). Точка: приёмка settle в MarkRelitInstall / demand-settle.

### Класс A (пустота) — в этом прогоне пробами не воспроизведён

- Группа «surface_valid=1, не нарисовано» × 2538 — вся **легитимная вода** (fluid block за пикселем, blue-dominant 2538/2538).
- `mesh_apply_stale_geom_accepted=206` накопительно — A1 жив, но координатной корреляции с дырами нет.
- Требуется: повторный witness с камерой в точке void-дыр (позиция пользователя на скриншоте) либо указание координат; stride 15–30.

### Счётчики свидетеля (финал)

`stale_geom_accepted=206`, `stale_light_accepted=813`, `relight_apply_n=0`, `pending_light_n=3`, missing=12, ready=109, `visual_holes=0` (детектор по-прежнему не видит неверные меши).

## 8. Результаты фикса B и уточнённый корень (2026-11-07, `feature/perf-0-30-deferred-eviction`)

Введена сверка после загрузки (`FinalizeCooperativeLoadForEnterGame`): не-air чанки с `LightFieldRevision<=1` получают синхронный `RelightChunk` + settle. Census (world245_fix2): `relit=920, rev0=0, rev1=817, rev2p=164` — reconcile отработал, **но чёрные пробы остались (72), field_lr чёрных чанков остался 1**.

**Уточнённый корень класса B: `kRelightFrontierIterationsColumn = 0`** (`ChunkLighting.h:17`). Колоночные relight'ы (load-фаза и runtime async) считают свет только своей колонки без frontier-перелива: тёмный регион колонок взаимно согласован (граничные условия соседей тоже тёмные), и ни один существующий путь, кроме edit-relight (у которого frontier-итерации есть), не может в него просветить. Отсюда и все наблюдения: чернота постоянна между сессиями, «лечится» установкой блока, stale/halo-сканы проходят.

**Фикс (следующий цикл, требует witness + perf-приёмку):** включить cross-column распространение — захват 3×3 колоночного окружения в async column relight (сейчас `column_center_only=true`, соседи — только face-шеллы) + 1–2 frontier-итерации в `UChunkRelightSnapshot::Compute` для колонкового пути. Стоимость: ~9× чанков на задачу (после union-флада — приемлемо), глубина конвейера уже капится. Альтернатива дешевле: frontier только для колонок, чьи соседи имеют более высокий свет (targeted).

Класс A (пустота) — ждёт повторный witness в точке дыр (позиция пользователя).

## 9. Результаты интерактивного witness и фикс void-класса (2026-11-07, `fbeafbdec`)

Интерактивная запись (world245_void2, видимое окно, пользователь у дыр, 42560 проб) поймала класс A и дала точный механизм:

- **Void**: 4657 проб — voxel-марш CPU упирается в твёрдые блоки (листва, hit_block 560/378) в чанках (9..10, 4, 18..20), ничего не нарисовано, вода позади. Состояние чанков: `des_g=6 pub_g=5/4` — **published-меш устарел относительно данных соседей, rebuild не завершается**: attempt churn (created→cancelled) при пассивном skip в pass-1 шедулера.
- **Корень**: pass-1 FirstMesh-lane скипает ЛЮБУЮ запись с drawable мешем (`HasDrawableGreedyMesh → skip`), не проверяя геометрический долг. Drawable-но-устаревший чанк никогда не перестраивается; edit лечит, потому что edit-путь перестраивает безусловно.
- **Чёрные**: 9303 проб кластером в (8..11, 3, 18..22) — `meshed_lr == field_lr` (11..28, relit многократно), `vertex_sky=0`, stale-скан молчит — **тот же самосогласованный тёмный регион, корень `kRelightFrontierIterationsColumn=0`** (раздел 8).

**Фикс** (`ChunkMeshCache.cpp` pass-1): drawable-запись с `desired_geom_rev > published_geom_rev` не скипается — реальный геометрический долг обязан перестраиваться независимо от residency устаревшего меша.

**Верификация** (world245_fix3, пользователь повторил маршрут, 71040 проб):
- mesh-дыры **4657 → 0**; чанки-должники полностью удовлетворены (ни одной demand-transition);
- патологический чёрный класс (реальные чанки, rev 1) — **0 проб**; оставшиеся «чёрные» пробы — чанк-заглушка (0,0) без привязки к геометрии (тёмная вода/контекст проб).

Осталось: cross-column frontier для чёрного класса (раздел 8) — отдельный witness + perf-цикл; финальная визуальная проверка пользователем на свежем мире.
