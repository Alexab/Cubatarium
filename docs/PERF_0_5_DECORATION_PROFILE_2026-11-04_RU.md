# PERF-0.5: профилирование и content-preserving оптимизация Decoration

Дата: 2026-11-04. Ветка: `feature/perf-0-5-decoration-profiling`.
База: `develop` после PERF-0.4 (`325606a02`).

## 1. Цель и реализованные изменения

PERF-0.4 показал, что Decoration даёт около половины post и большие хвосты. В этом этапе:

1. Добавлена агрегация по ключу `(pool, rule index, feature key)` для Decoration: число
   оценок и кандидатов, попытки и успешные размещения, время оценки и placement.
2. Для worldgen-проверки префаба считаются фактические посещения вокселов в трёх циклах
   `CanPlaceObjectAtForWorldGen` с учётом ранних выходов и явные вызовы
   `FindTopSolidSurfaceY`. Это не оценка по размеру prefab.
3. Агрегаты накапливаются thread-local и сбрасываются в общую сводку один раз на чанк.
   Mutex не используется в цикле колонок. Подробная телеметрия включается существующим
   `CUBATARIUM_WORLDGEN_SEAL_AUDIT=1`.
4. `movement_diagnostics.json` получил независимый `object_feature_summary` схемы
   `object_feature_rules.v1`; формат `populate_summary` не изменён.
5. По результатам измерений deterministic chance/density-gate перенесён после biome/subbiome
   фильтров, но до surface lookup, prefab lookup, ecology и gradient. Gate зависит только от
   правила, координат и неизменяемых настроек. Старые и новые условия образуют одну
   конъюнкцию: принятые кандидаты, их веса, hash выбора и placement не меняются. Методы
   чтения мира не имеют побочных эффектов; ранний отказ раньше лишь пропускает дальнейшие
   проверки для правила, которое гарантированно не попало бы в candidates.

Это не оптимизация путём снижения density и не изменение таблицы правил.

## 2. Протокол

Release `Cubatarium`, 1280×720, `--metrics`, исходная копия
`World_242_perf_baseline_source`; каждый прогон использует отдельную новую копию.
Пользовательский `World_242` не изменялся.

- 8 с начального idle;
- 70 с sprint-полёта на запад без телепортации, level-forward;
- 30 с остановки;
- warmup 20 с;
- `CUBATARIUM_WORLDGEN_SEAL_AUDIT=1`.

До: `bin/suite_reports/perf_0_5/moving_1/`, `moving_2/`.
После: `bin/suite_reports/perf_0_5/post_1/`, `post_2/`.
Во всех четырёх `flight_sim_report.json`: `exit_code=0`. Возвращаемый runner'ом
`pass=false` отражает старые performance/readiness gates, а не аварию приложения.

## 3. Профиль до оптимизации

| Метрика | moving_1 | moving_2 |
|---|---:|---:|
| Завершено / отменено чанков | 166 / 0 | 160 / 0 |
| Decoration, сумма | 17,08 с | 19,16 с |
| Decoration, median / p95 | 5,25 / 402,16 мс | 4,71 / 467,61 мс |
| Сумма rule evaluation | 16,17 с | 18,35 с |
| `lily_pad_pair` evaluation | 15,55 с | 17,61 с |
| Все prefab voxel visits | 4 671 | 4 778 |
| Все prefab surface scans | 1 811 | 1 822 |

`lily_pad_pair` даёт 96,18 % и 95,96 % времени rule evaluation, или 91,03 % и 91,93 %
всей стадии Decoration. Правило оценивалось 16 145 / 15 960 раз, но давало только 78 / 72
кандидата. Причина — водный surface lookup с окрестностью до density-gate со spacing 48.

Placement всех Decoration занимает 72,6 / 92,1 мс. Voxel-проверки немногочисленны и не
объясняют многие секунды стадии. Поэтому caching prefab или микрооптимизация voxel loop не
были выбраны: они не адресуют измеренный dominant cost.

## 4. Результат после переноса gate

| Метрика | post_1 | post_2 |
|---|---:|---:|
| Завершено / отменено чанков | 170 / 0 | 192 / 0 |
| Полный populate, сумма | 61,23 с | 57,61 с |
| Post, сумма | 18,48 с | 16,13 с |
| Decoration, сумма | 0,94 с | 0,82 с |
| Decoration, median / p95 | 3,14 / 14,66 мс | 2,75 / 10,68 мс |
| `lily_pad_pair` evaluation | 0,314 с | 0,209 с |
| `lily_pad_pair`: candidates / placed | 71 / 55 | 85 / 70 |
| Все Decoration: candidates / placed | 531 / 303 | 624 / 350 |

На повторном маршруте Decoration стал примерно на 18–23 раза дешевле по суммарному
worker wall time; p95 уменьшился примерно в 27–44 раза. Маршруты создают разное число
чанков, поэтому сравнение сумм служит ориентиром, а не точным нормированным speedup.
Количество кандидатов и успешных размещений после изменения не снизилось.

Парность следует из чистой перестановки независимых условий одной конъюнкции и
подтверждается регрессионными тестами. Полный побайтовый snapshot сгенерированных чанков
между отдельными старым/новым executable в этом этапе не сохранялся; счётчики разных
динамических прогонов не выдаются за такой snapshot.

## 5. FPS и оставшиеся симптомы

| Прогон | Fly median, мс | Effective fly FPS |
|---|---:|---:|
| moving_1 | 31,87 | 31,38 |
| moving_2 | 30,90 | 32,36 |
| post_1 | 27,35 | 36,57 |
| post_2 | 29,90 | 33,44 |

Есть сопутствующее улучшение, но два динамических прогона с общей телеметрией не отделяют
его полностью от машинного и scheduler-шума. Нельзя приписывать весь FPS-дельта только
Decoration.

Старые проблемы остаются видимыми: `post_stop_missing_max` равен 44 / 44 / 44 / 45;
маршруты по-прежнему не проходят readiness gates. Во втором post-прогоне число spike-записей
увеличилось до 16, несмотря на ускорение populate. Следовательно, этап не утверждает, что
устранены отставание визуала за пределами кольца, мгновенные дыры при разрушении блока или
задержка готовности света. Для них нужны отдельные commit/admission/mesh/relight этапы.

## 7. Следующий шаг

PERF-0.5 принят: горячий водный lookup устранён для колонок, отклонённых density-gate,
без изменения параметров контента. Следующий отдельный этап должен профилировать внутренние
проходы permeable seal. Независимо от него нужна трассировка publish/readiness/relight и
edit-remesh пути: именно они остаются кандидатами для наблюдаемых визуальных задержек.
